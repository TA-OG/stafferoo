# Stafferoo single autonomous build guide, consolidated from your files

This is the single source of truth a coding agent should follow to build the whole MVP end to end, in the correct order, with no drift. It merges product, policy, payments, engineering rules, and delivery slices from your docs.

---

## 1. Canonical definitions and naming

1. App name: Stafferoo, domain: stafferoo.app
2. Roles
   1. Staff, individual workers who accept shifts
   2. Settings, businesses who post shifts and pay
   3. Admin, platform operator for verification, disputes, enforcement
3. Terms used in UI and copy
   1. Call buyers “settings” and describe them publicly as “businesses” on the marketing site
   2. Call workers “staff” in product and code
   3. Keep language human, clear, non corporate

---

## 2. Non negotiables, engineering and delivery contract

Every agent must follow these, always.

1. Stack baseline
   1. Next.js App Router
   2. TypeScript strict
   3. Postgres with migrations
   4. Background jobs via jobs table plus Node worker process
   5. Zod validation for all inputs
   6. Feature flags by default
   7. Observability first, structured logs plus audit events, correlation ids
2. Quality gates, required after every slice
   1. Lint passes
   2. Typecheck passes
   3. Tests pass
   4. Build passes
3. Slice discipline
   1. One small feature per slice
   2. Contract first APIs, define request and response schemas and error codes
   3. Lightweight threat model per slice, identify abuse cases and mitigations
   4. No scope creep, anything extra goes to backlog
   5. No silent failures, no best effort success, never treat upstream errors as valid
4. Data safety rules
   1. No sensitive payloads in logs
   2. Private storage buckets for documents, signed URLs only for admin preview
   3. Freemium views must return only safe, non identifying fields
5. Security rules
   1. Least privilege, secrets never committed
   2. Webhooks must be idempotent and retry safe
   3. Admin overrides require mandatory reason and audit event

## 3. Product scope, what the MVP must do

### 3.1 Core marketplace loop, MVP goal

Prove a working marketplace loop with compliance gating:

1. Settings register, get verified, then can view supply in freemium mode
2. Staff register, complete onboarding, submit documents, pass verification, then can respond to jobs
3. Settings can post a job and confirm booking only with an active subscription
4. Admin can audit and approve key compliance items, and enforce basic reliability controls

### 3.2 Explicit MVP non goals, defer until later

1. Precise travel time routing and distance matrix logic
2. SMS and push, email only is acceptable for MVP
3. In app chat, until after booking loop works
4. Full strike automation, beyond basic status fields if needed
5. Automated DBS verification can be deferred to manual recording for MVP, but you already have a production plan to implement as a later slice behind a flag

## 4. Business model, pricing, rollout controls

### 4.1 Pricing and unit economics, current agreed direction

Use these as configurable values stored server side, not hard coded in UI.

1. Subscription tiers for settings
   1. Standard, £249 per setting per month
   2. Multi site, £249 per group per month plus £99 per additional location
   3. Enterprise, uplift, includes advanced governance, approvals, reporting, integrations, priority support
2. Marketplace hourly pricing
   1. Charge settings per hour, £22 or £23 appears in different documents, treat this as a configuration value, set the MVP default to the value used in the codebase business decision file for this repo and store it in a single pricing config table so it can be changed without code change
   2. Pay staff per hour, £15.50
3. Annual option
   1. Pay 10 months equivalent per year
4. Payment terms and cadence
   1. Settings subscription billed pro rata on signup, then aligned so everyone pays on the 28th for the next month
   2. Settings pay for staff hours booked the previous week on the Wednesday after
   3. Staff work a week in hand, paid weekly after, invoice submitted Friday, staff confirm hours and flag discrepancies
   4. Settings receive a notification to confirm hours and invoice, payment expected within 3 days

### 4.2 Growth control, waitlist and density gating

1. Onboard staff first, build verified supply density by postcode cluster
2. Invite settings only after a cluster meets minimum supply thresholds
3. Admin dashboard must track density metrics and allow controlled go live by postcode clusters, with audit logged overrides
4. Expansion gates must be met for the last 28 days before enabling a new cluster, fill rate, no show, late cancellation, compliance pass, dispute rate

## 5. Policies and enforcement logic, product requirements

### 5.1 Cancellations

Implement tiered cancellation tiers and fee outcomes as policy engine logic, stored as data, not hard coded.

Settings cancellation tiers

1. Less than 2 hours, fee 100 percent
2. 2 to 12 hours, fee 50 percent
3. 12 to 23 hours, fee 25 percent
4. 24 plus hours, free

Staff cancellation tiers

1. 24 plus hours, no proof, no strike
2. 12 to 24 hours, explanation, admin review
3. 2 to 12 hours, evidence plus explanation, urgent review
4. Less than 2 hours, must contact support plus evidence, strike unless genuine emergency

### 5.2 Strikes, suspensions, bans

Implement the progression as a policy layer, with an audit trail and expiry logic.

1. Strike 1, warning, hidden from settings, expires after 90 days clean
2. Strike 2, visible warning to settings, ranking penalty, expires after 90 days clean
3. Strike 3, 30 day suspension, hidden from search, automatic reactivation, then probation
4. Strike 4, 60 day suspension if within 30 days after strike 3 lifted, cancellations, manual review to reactivate
5. Strike 5, permanent ban, block re registration using DBS number or other fraud key

### 5.3 No show protocol with secondary cover

MVP can start with a simplified version but the data model must support it from day one.

1. Primary and setting both get check in prompt at start time
2. If no response, reminders
3. At 15 minutes, trigger no show flow, notify secondary and ask setting to wait or mobilise backup
4. If backup mobilised, secondary gets emergency bonus, primary loses shift but gets travel compensation, primary gets strike

## 6. Onboarding and verification, exact requirements

### 6.1 Staff onboarding, hard stops

Implement the full data capture and hard stops exactly.

Step 1 account creation

1. Full name
2. Email
3. Password
4. Email verification

Step 2 profile basics

1. Photo optional
2. National insurance
3. Mobile number
4. Location postcode
5. Travel radius
6. Mode of transport
7. Role skills
8. DBS Update Service, yes progress, no hard stop, but later rule says staff must be on update service, so treat as hard stop for MVP unless explicitly waived behind an admin override flag
9. Must tick declaration for DBS online status check consent
10. Declare spent or unspent convictions with details and dates
11. Childcare qualification level, none is hard stop for MVP and route to keep on file page
12. Years of childcare experience
13. Other qualifications, food hygiene, SEN
14. Disabilities
15. Support adjustments
16. Health concerns implications

References requirement

1. References must include at least one setting reference using a work email from the setting domain, not gmail and similar personal domains
2. Most recent employer reference must capture URN, name, position, setting name
3. Also capture one personal or professional reference and one professional reference
4. Reference requests must send a unique link to referees, token based, one time use

Step 3 document upload

1. ID, passport or driving licence
2. Right to work
3. Qualifications evidence
4. Enhanced DBS, update service
5. Surname on DBS certificate
6. Certificate number
7. Safeguarding certificate plus completion date, expiry warnings
8. Paediatric first aid certificate plus completion date, expiry warnings
9. Disqualification declaration, not living with anyone disqualified
10. Emergency contacts, two
11. GP details
12. Health declaration questionnaire plus details textbox
13. Digital signature plus date
14. Staff declaration text included exactly as provided
15. Emergency medical treatment permission selection

Step 4 verification status

1. Pending review
2. Verified badge once admin approves

Step 5 availability setup

1. Available now toggle
2. Calendar optional for MVP

### 6.2 DBS Update Service verification, production implementation, later slice behind a flag

You have a full production plan and schema for async verification, worker parsing XML, strict outcome mapping, idempotency, retries, never treat errors as valid. Implement this as its own feature cluster with a flag.

## 7. Settings onboarding, freemium supply view, subscription gating

1. Settings registration must capture Ofsted URN and verification status, admin queue for approve or reject with notes, audit logged decisions
2. Freemium model
   1. Settings can sign up for free
   2. Free tier can see counts of staff within radius and blurred preview list
   3. Preview list fields, initials, blurred avatar token, qualification badge, years experience, ID verified badge, Enhanced DBS Update Service verified badge
   4. No identifying details, no contact, no full postcode, no documents
   5. Extended radius group shows staff just outside radius, described as an additional hour of travel, distinct background styling
3. Paid tier gate
   1. Subscription required when a setting posts a job or confirms booking hours
   2. If no active subscription, show paywall and require subscription before continuing
4. Subscription billing alignment
   1. Pro rata on signup
   2. Align renewal to 28th

## 8. Data model, minimum required tables

Use the schema ideas from the technical spec and master guide, but align with Stafferoo architecture, Postgres migrations, and RLS.

Minimum tables for MVP loop

1. users, roles, sessions, organisation membership, or tenancy model
2. staff_profiles, staff_documents, staff_verifications summary
3. setting_profiles, setting_documents if needed, setting_verification status
4. reference_requests, reference_responses, token hash, expiry, one time submit
5. jobs or job_requests, booking_responses, bookings or placements, with primary and secondary staff support
6. subscriptions or billing_events, store subscription status, tier, renewal alignment
7. audit_events, required for sensitive actions
8. feature_flags, required for safe rollout
9. jobs queue, worker heartbeats, for async tasks
10. enforcement tables, strikes, suspensions, banned keys, cancellations, even if minimal in MVP

Storage buckets

1. staff documents, private
2. setting documents, private
3. signed URLs, never public buckets for sensitive documents

## 9. Build order, single authoritative slice plan

Use this order. Each slice must include: plan, acceptance criteria, threat model, contracts, migrations, tests, and must pass gates.

### Slice group 0, repo hardening and baseline

1. Add docs folder and ADRs, lock architecture baseline and worker pattern
2. Add feature flag system, admin UI, audit events for toggles
3. Add audit events infrastructure and correlation ids
4. Add auth and RBAC skeleton, tenancy enforcement, tests
5. Add background jobs table and worker framework, dummy job end to end, retries, stale lock recovery, heartbeat

### Slice group 1, settings onboarding and freemium supply

1. Settings registration, Ofsted URN capture, verification workflow, admin queue, audit log
2. Freemium staff supply view, safe fields only, within radius and extended radius grouping, distinct styling

### Slice group 2, staff onboarding and compliance gating

1. Staff onboarding UI skeleton with steps, draft save, resume, admin queue for submitted packs
2. Implement full staff onboarding fields, uploads, declarations, health section, signature, hard stops for qualification and DBS update service rules
3. References workflow, request tokens, public referee form, work email domain rule for the setting reference, admin review and approve, audit events

### Slice group 3, booking loop and subscription gating

1. Settings subscription skeleton, tiers, status, pro rata then align to 28th, subscription required for posting or confirming booking
2. Job posting, staff discovery and response, setting selects primary and confirms booking, email notifications for key events
3. Booking management views for settings, booking status page for staff

### Slice group 4, policy enforcement primitives

1. Cancellation policy engine tables and calculations, admin review path for staff cancellations requiring evidence, audit events
2. Strikes and suspension primitives with expiry logic and visibility rules, admin actions audited
3. No show protocol scaffolding, check in prompts and secondary standby support in data model, even if notifications are email first in MVP

### Slice group 5, payments safety and later automation

1. Store invoice records for bookings, weekly staff invoicing concept, Wednesday billing concept, notify settings to approve hours, enforce expected within 3 days, keep money movement minimal in MVP
2. Stripe billing subscriptions, idempotent webhooks, retries, audit trail, behind a feature flag until tested in staging

### Slice group 6, admin rollout and density dashboard

1. Postcode cluster model, metrics tables, scheduled job to compute cluster metrics and alerts
2. Admin dashboard showing coverage and rollout state, green amber red flags, go live controls, audit logged reasons
3. Auto pause safeguard if live cluster breaches guardrails for 7 days

### Slice group 7, DBS Update Service automated verification, production grade

Implement exactly as the DBS plan, async, strict mapping, idempotency, retries, raw response retention purge, unit and integration tests, and keep behind a flag until stable.

## 10. Definition of done for the whole MVP

The MVP is only “done” when all are true:

1. A setting can sign up, be verified by admin, and see freemium supply without any personal data leakage
2. A staff member can sign up, complete onboarding, upload documents, submit references, and reach pending review state
3. Admin can approve staff and settings, with audit events for each decision
4. Subscription gating prevents job posting and booking confirmation when inactive, but allows freemium browsing
5. Booking loop works end to end, post job, staff respond, setting confirms, both see status, email notifications sent
6. Cancellation and strikes primitives exist with correct policy tiers and audit trail
7. Gates pass on the repo, lint, typecheck, test, build
